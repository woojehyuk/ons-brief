# tasks — 한국어 실행 지침

실행 환경: `.specify/` 프로젝트 구조와 Bash/Python.

먼저 프로젝트 루트의 [공통 실행 규칙](../../../.specify/docs/workflow-common.md)을 읽는다.
사용자 입력은 `$ARGUMENTS`와 호출 메시지에서 확인한다. 본 작업 전 `hooks.before_tasks`, 본 작업 후 `hooks.after_tasks`을 공통 규칙에 따라 처리한다.

## 절차

1. `.specify/scripts/bash/setup-tasks.sh --json`을 실행해 `FEATURE_DIR`, `AVAILABLE_DOCS`, `TASKS_TEMPLATE_CONTENT`, `TASKS_TEMPLATE`을 읽는다. 구형 스크립트에 내용 키가 없을 때만 경로의 템플릿을 읽는다.
2. 필수 `spec.md`·`plan.md`, 확정 원칙, 존재하는 설계·조사·검증 문서를 읽는다. 기존 `tasks.md`가 있으면 ID, 완료 상태, 의존성과 사용자 편집을 보존하며 필요한 변경만 한다. 완료 작업을 초기화하거나 기존 ID를 다른 의미로 재사용하지 않는다.
3. 사용자 스토리 우선순위에 따라 실제 작업을 분해한다. 공통 기반은 그것을 요구하는 스토리만 차단한다. 이미 갖춘 프로젝트 구조·인증·DB 등을 재생성하는 작업은 넣지 않는다.
4. 각 기능 요구사항·구현 가능한 성공 기준·인수 시나리오를 작업에 연결한다. 출시 후 사업 지표는 측정/운영으로 구분하고 구현 누락으로 취급하지 않는다.
5. 작업마다 구체적 행동, 실제 대상 경로, 관련 `FR-###`/`SC-###`/`USn/ACn`, 완료 기준을 적는다. 파일 수정이 없는 실행·조사 작업은 검증 대상 또는 산출물 경로를 적고 가짜 파일명을 만들지 않는다.
6. 테스트는 사용자·명세·원칙의 요구와 변경 위험에 따라 추가한다. TDD가 요구되면 대응 구현 전에 테스트 실패를 확인한다. 기존 필수 검사와 각 스토리의 독립 검증은 누락하지 않는다.
7. 중복 ID, 누락 경로·추적 근거, 미정 자리표시자, 의존성 순환, 선행 작업 누락, 잘못된 병렬 표시를 검토한다. 사용자 지정 MVP 범위가 있으면 그에 맞추되 나머지 범위를 임의 삭제하지 않는다.

## 작업 형식과 의존성

```text
- [ ] T001 [P] [US1] src/example.py에서 기능 구현 (FR-001; 완료 기준: 지정 시나리오 통과)
```

- `T` 뒤 숫자는 최소 3자리다. 새 ID는 기존 최댓값 다음부터 배정하며 `T1000` 이상도 허용한다.
- `[P]`는 같은 단계에서 함께 실행할 수 있고 파일·공유 자원 충돌이 없으며 선행 의존성이 충족된 작업에만 붙인다. 표시 자체가 에이전트 위임을 지시하지 않는다.
- 스토리 단계에는 `[US1]` 같은 표식을 붙이고 공통 준비·기반·마무리에는 생략한다.
- `## Phase N: 한국어 단계명` 형식을 유지한다. 필요한 준비/기반 → 스토리별 단계 → 필요한 마무리로 구성하되 빈 단계는 만들지 않는다.
- 의존성은 작업 ID 또는 스토리 간 관계로 명시한다. 병렬 가능 묶음과 검증 지점을 실제로 필요한 만큼만 제시한다.

## 완료 보고

`tasks.md` 경로, 전체·스토리별 작업 수, 범위와 MVP, 의존성·병렬 가능 작업, 검증 방법, 형식·요구사항 포괄 여부를 요약한다. 필요하면 `$speckit-analyze`, 준비되었으면 `$speckit-implement`로 이어진다.
