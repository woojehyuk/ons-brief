# plan — 한국어 실행 지침

실행 환경: `.specify/` 프로젝트 구조와 Bash/Python.

먼저 프로젝트 루트의 [공통 실행 규칙](../../../.specify/docs/workflow-common.md)을 읽는다.
사용자 입력은 `$ARGUMENTS`와 호출 메시지에서 확인한다. 본 작업 전 `hooks.before_plan`, 본 작업 후 `hooks.after_plan`을 공통 규칙에 따라 처리한다.

## 절차

1. `check-prerequisites.sh --json --paths-only`로 기능 경로를 확인하고 `spec.md`를 읽는다. 누락 시 `$speckit-specify`를 안내한다. 중요한 요구사항 미결정은 계획에서 임의로 확정하지 않는다.
2. `.specify/scripts/bash/setup-plan.sh --json`을 실행해 `FEATURE_SPEC`, `IMPL_PLAN`, `SPECS_DIR`, `BRANCH`를 읽는다. 이 스크립트는 기존 계획을 보존한다. 새 파일이 비어 있거나 템플릿 해석 경고가 나면 해결 후 진행한다.
3. 기존 코드·계획·확정 원칙과 합성된 `plan-template`을 읽는다. 실제 저장소에 맞게 기술 맥락과 원칙 준수 검사를 작성한다. 사용자 지정 기술과 기존 구조를 존중한다.
4. 조사 단계: 결정에 영향을 주는 미확정 기술·연동·의존성만 조사한다. 필요한 경우 공식 자료를 확인하고 `research.md`에 결정, 이유, 대안, 출처, 남은 불확실성을 기록한다. 이미 근거가 충분하면 기존 기록을 참조한다. 조사할 내용이 없으면 별도 조사 문서를 강제하지 않는다.
5. 설계 단계: 해당 기능에 필요한 산출물만 만든다.
   - `data-model.md`: 데이터가 있을 때 개체·속성·관계·식별·검증·상태 전이.
   - `contracts/`: 외부에 노출하는 API, CLI, 라이브러리 또는 UI 계약이 있을 때 입력·출력·오류·호환성.
   - `quickstart.md`: 실행 전제, 설정, 검증 명령/수동 절차, 예상 결과. 기존 안내를 참조하고 전체 구현 코드나 테스트 모음을 복제하지 않는다.
6. 계획에 실제 변경 경로, 요구사항과 설계의 연결, 검증 전략을 적는다. 해당하는 경우에만 배포·마이그레이션·되돌리기·관측성 위험을 기록한다. 원칙 검사는 조사 전과 설계 후 수행하고, 허용되지 않은 위반은 해결할 때까지 준비 완료로 보고하지 않는다.
7. 미해결 `NEEDS CLARIFICATION`, 근거 없는 결정, 불필요한 구조 예시를 제거하거나 명시적으로 보류한다. 가정과 확인된 사실을 구분한다.

## 완료 보고

`IMPL_PLAN`과 생성·갱신·생략한 설계 문서, 검증 방법, 미결정·원칙 검사 결과를 보고한다. 이 단계는 설계까지이며 작업 목록은 `$speckit-tasks`에서 만든다. 사용자가 더 넓은 연속 작업을 요청했다면 그 범위에 따라 이어간다.
