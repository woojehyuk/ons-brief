# checklist — 한국어 실행 지침

실행 환경: `.specify/` 프로젝트 구조와 Bash/Python.

먼저 프로젝트 루트의 [공통 실행 규칙](../../../.specify/docs/workflow-common.md)을 읽는다.
사용자 입력은 `$ARGUMENTS`와 호출 메시지에서 확인한다. 본 작업 전 `hooks.before_checklist`, 본 작업 후 `hooks.after_checklist`을 공통 규칙에 따라 처리한다.

## 소유권

이 스킬은 요구사항 문서의 품질을 묻는 항목을 만들거나 추가한다. 생성한 항목은 모두 `[ ]`로 둔다. 검토자는 직접 또는 명시적으로 요청한 평가를 통해 판정한다. `checklists/requirements.md`는 내장 점검표이므로 사용자 정의 파일명으로 사용하지 않는다.

## 절차

1. `.specify/scripts/bash/check-prerequisites.sh --json --paths-only`로 기능 경로를 읽고 `spec.md` 존재를 확인한다. 계획 전에 사용할 수도 있으므로 `plan.md`를 필수로 요구하지 않는다.
2. `.specify/scripts/bash/resolve-template.sh checklist-template --json`의 `TEMPLATE_CONTENT`를 읽는다. 명세와 확정 원칙, 존재하는 계획·작업 중 요청 주제와 관련된 부분을 읽는다.
3. 사용자 요청에서 주제, 독자, 시점, 깊이, 제외 범위를 정한다. 내용에 실질적으로 영향을 주는 미정 사항만 처음에 최대 3개 질문하고 필요한 후속 질문을 포함해 최대 5개로 제한한다. 이미 정해진 내용은 다시 묻지 않는다. 답이 없어도 진행 가능한 경우 표준 깊이·관련 핵심 주제로 작성하고 가정을 밝힌다.
4. 주제에 맞는 `checklists/<domain>.md`를 사용한다. 기존 파일은 읽고 동등한 항목은 중복 추가하지 않는다. 새 항목만 추가하며 기존 문구·상태·순서를 보존한다. ID는 파일 내 기존 `CHK` 번호의 최댓값 다음부터 최소 3자리로 배정한다.
5. 완전성·명확성·일관성·측정 가능성·인수 기준·시나리오·관련 경계 사례·비기능 요구·가정/의존성 중 필요한 범주를 선택한다. 범위 밖 보안·배포 등 범주를 기계적으로 추가하지 않는다.
6. 각 항목은 요구사항이 명시되었는지, 충분히 구체적인지, 서로 일치하는지를 묻는다. 문서 절·요구사항 ID를 연결하고 누락이면 `[Gap]`, 모호성이면 `[Ambiguity]`, 충돌이면 `[Conflict]`, 가정이면 `[Assumption]`을 적어 근거 상태를 드러낸다.
7. 중복·무관한 항목을 합치거나 제외한다. 약 40개를 넘으면 영향도 순으로 줄이되 중요한 요구를 수량 때문에 누락하지 않는다. 기존 파일은 자동 정리·삭제하지 않는다.

## 항목 예시

```text
- [ ] CHK001 권한이 없는 사용자의 오류 응답이 명세에 정의되어 있는가? [완전성, Spec §FR-001]
- [ ] CHK002 검색 응답 목표의 측정 조건과 허용 시간이 명시되어 있는가? [명확성, Spec §SC-001]
- [ ] CHK003 외부 서비스 응답 지연 시 사용자에게 제공할 동작이 정의되어 있는가? [Gap]
```

“버튼이 제대로 작동하는가?”는 구현 검증이다. “버튼 활성화 조건이 정의되어 있는가?”는 요구사항 품질 검토다. 클릭·API 같은 단어 자체를 금지하지 말고 판단 대상을 구분한다.

## 완료 보고

파일 경로, 신규/추가 여부, 추가 항목 수와 전체 수, 주제·깊이·독자·가정을 보고한다. 생성만으로 검토가 완료되었다고 표현하지 않는다.
