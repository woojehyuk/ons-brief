# taskstoissues — 한국어 실행 지침

실행 환경: `.specify/` 프로젝트 구조와 Bash/Python.

먼저 프로젝트 루트의 [공통 실행 규칙](../../../.specify/docs/workflow-common.md)을 읽는다.
사용자 입력은 `$ARGUMENTS`와 호출 메시지에서 확인한다. 본 작업 전 `hooks.before_taskstoissues`, 본 작업 후 `hooks.after_taskstoissues`을 공통 규칙에 따라 처리한다.

## 절차

1. `check-prerequisites.sh --json --paths-only`로 기능 경로를 확인하고 `tasks.md`와 필요한 명세·계획·원칙을 읽는다. 코드 펜스 밖 작업 줄에서 체크 상태, `T` 뒤 최소 3자리 숫자, 선택적인 `[P]`·`[USn]`, 설명을 분리한다. 중복 작업 ID는 먼저 해결한다.
2. `git config --get remote.origin.url`로 실제 대상 저장소를 확인한다. GitHub HTTPS/SSH 주소에서 호스트·소유자·저장소를 정확히 해석한다. GitHub가 아니거나 해석이 모호하면 생성하지 않는다. 검증된 원격과 다른 저장소에는 생성하지 않는다.
3. 완료 작업은 기본적으로 생성을 생략한다. 사용자가 완료 작업까지 요청했다면 포함하되 완료 사실을 본문에 명시한다. 실제 이슈 생성 요청이 없다면 제목·본문 초안까지만 작성한다.
4. 중복 키는 작업 ID만 사용하지 않고 저장소·기능 경로·작업 ID를 함께 사용한다. 이슈 본문에 `<!-- speckit-task: specs/001-feature:T001 -->`처럼 기능 경로와 ID 표식을 넣는다. 같은 저장소의 다른 기능 `T001`과 혼동하지 않는다.
5. 사용 가능한 GitHub 도구 또는 CLI로 열린/닫힌 이슈를 모두 조회한다. 도구의 실제 스키마에 맞춰 상태와 페이지네이션을 명시한다. 상태 생략이 전체 조회라고 가정하지 않는다. 커서/페이지를 끝까지 확인하되 대상 키가 모두 확인되면 중단한다.
6. 기존 표식이 같은 이슈는 재사용한다. 이전 형식 이슈는 제목의 `\bT\d{3,}\b`와 본문의 기능 경로·명세 링크를 함께 확인한다. 제목 ID만 일치하여 기능을 알 수 없으면 모호한 후보로 보고하고 해당 작업의 생성을 보류한다.
7. 누락된 작업의 제목은 `T001: 설명`처럼 ID를 한 번만 쓴다. 본문에는 기능 경로, 출처 요구사항/스토리, 변경 경로, 완료 기준, 의존 작업과 이미 알려진 이슈 링크를 포함한다. 선행 작업부터 생성하며 성공한 키→URL 매핑을 즉시 보존한다.
8. 요청 시간 초과나 일부 실패가 나면 성공 여부가 불명확한 이슈를 키로 다시 조회한 뒤 누락된 것만 재시도한다. 인증·권한 문제나 반복 실패는 멈추고 생성·재사용·실패 목록을 보고한다. 확인하지 않은 이슈 생성 요청을 반복하지 않는다.

## 완료 보고

대상 저장소, 기능 경로, 생성/재사용/완료로 생략/모호하여 보류/실패 수와 이슈 URL을 보고한다. `tasks.md`의 완료 표시는 변경하지 않는다.
