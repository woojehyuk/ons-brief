# analyze — 한국어 실행 지침

실행 환경: `.specify/` 프로젝트 구조와 Bash/Python.

먼저 프로젝트 루트의 [공통 실행 규칙](../../../.specify/docs/workflow-common.md)을 읽는다.
사용자 입력은 `$ARGUMENTS`와 호출 메시지에서 확인한다. 본 작업 전 `hooks.before_analyze`, 본 작업 후 `hooks.after_analyze`을 공통 규칙에 따라 처리한다.

## 범위

파일을 수정하지 않는다. 분석 보고와 구체적인 수정 제안만 작성한다. 훅에도 읽기 전용 범위를 적용한다. 별도로 요청된 수정은 분석 결과와 구분된 후속 작업으로 수행할 수 있다.

## 절차

1. `.specify/scripts/bash/check-prerequisites.sh --json --paths-only`로 경로를 읽고 `spec.md`, `plan.md`, `tasks.md`가 모두 있는지 별도로 확인한다. 누락 시 대응하는 `specify`/`plan`/`tasks` 스킬을 안내한다. 일반 사전 검사 모드의 메타데이터 저장을 피한다.
2. 명세의 범위·스토리·인수 기준·요구사항·성공 기준, 계획의 기술 결정·구조·제약, 작업의 ID·의존성·병렬 표식·경로와 확정 원칙을 읽는다. 필요한 부분부터 읽고 부족할 때 확장한다.
3. `FR-###`, `SC-###`, `USn/ACn`을 기준으로 의도 목록과 작업 연결을 만든다. ID가 없으면 안정적인 의미 키를 쓴다. 구현 가능한 성공 기준은 포괄률에 포함하고 출시 후 사업 지표는 분리해 보고한다. 추정 연결은 명시적 연결과 구분한다.
4. 다음을 검사한다: 중복 요구, 모호한 표현·미해결 표식, 주체/결과/인수 기준 누락, 원칙 충돌, 작업이 없는 요구와 근거 없는 작업, 용어·개체·기술 결정 불일치, 잘못된 순서·순환 의존성·파일 충돌.
5. 실제 문서 위치와 근거를 가진 발견만 기록한다. 핵심 발견은 최대 50개, 초과분은 범주별로 요약한다. 동일 입력에는 일관된 ID와 집계를 사용한다.

## 심각도

- `CRITICAL`: 확정 원칙의 필수(MUST) 위반 또는 핵심 기능을 막는 누락.
- `HIGH`: 상충·중복 요구, 중요한 보안/성능 모호성, 검증 불가능한 인수 기준.
- `MEDIUM`: 용어 불일치, 부가 요구의 포괄 누락, 불명확한 경계 사례.
- `LOW`: 실행에 영향을 주지 않는 표현·중복 개선.

## 보고

발견 표는 `ID | 범주 | 심각도 | 파일:줄 | 근거·영향 | 수정 제안`으로 작성한다. 요구사항별 연결 작업 표, 원칙 충돌, 미연결 작업, 전체 요구·작업 수, 포괄률, 모호성·중복·치명적 발견 수를 포함한다. 분모가 0이면 포괄률을 해당 없음으로 표시한다.

치명적 문제가 있으면 구현 전에 해결하도록 안내한다. 문제가 없으면 확인 범위와 0건 결과를 보고한다. 누락 문서를 존재하는 것처럼 해석하거나 보고서 작성만으로 구현 품질을 보장하지 않는다.
