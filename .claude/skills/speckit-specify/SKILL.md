# specify — 한국어 실행 지침

실행 환경: `.specify/` 프로젝트 구조와 Bash/Python.

먼저 프로젝트 루트의 [공통 실행 규칙](../../../.specify/docs/workflow-common.md)을 읽는다.
사용자 입력은 `$ARGUMENTS`와 호출 메시지에서 확인한다. 본 작업 전 `hooks.before_specify`, 본 작업 후 `hooks.after_specify`을 공통 규칙에 따라 처리한다.

## 절차

1. 기능 설명에서 사용자, 목표, 행동, 데이터, 범위와 제약을 추출한다. 입력이 없을 때만 기능 설명을 요청한다.
2. 신규 작성인지 기존 기능 갱신인지 구분한다. 갱신은 명시된 경로나 현재 기능의 `spec.md`를 읽고 수정하며 새 디렉터리를 만들지 않는다. 대상이 모호하면 확인한다.
3. 신규 기능은 한 번의 호출에서 하나만 만든다. 짧은 영문 kebab-case 이름을 정한다. 명시된 `SPECIFY_FEATURE_DIRECTORY`가 있으면 그대로 사용한다. 없으면 `.specify/init-options.json`의 `feature_numbering`에 따라 `data/specs/<접두사>-<이름>`을 정한다.
   - `timestamp`: 현재 시각의 `YYYYMMDD-HHMMSS`.
   - `sequential` 또는 생략: 기존 순차 번호의 최댓값 다음 번호, 최소 3자리. 타임스탬프 접두사는 순차 번호에서 제외한다.
   - `feature_numbering`이 없고 `branch_numbering`만 있으면 호환용으로 읽고 새 키로 이전하라는 안내를 남긴다.
   - 충돌한 경로의 기존 명세를 덮어쓰지 않는다. 명시 경로의 기존 문서는 갱신 여부를 판단한다.
4. `spec-template`을 합성 해석하고 성공한 뒤 신규 `spec.md`의 시작 내용으로 쓴다. 갱신 시에는 구조만 참조한다. `.specify/feature.json`의 `feature_directory`에 실제 선택 경로를 저장한다. 환경변수 이름 자체를 값으로 저장하지 않는다.
5. `before_specify` 훅이 실제 브랜치를 만들었을 때만 반환된 `BRANCH_NAME`/`FEATURE_NUM`을 참고한다. 모든 사전 훅이 브랜치를 만든다고 가정하지 않는다. 사용자의 `GIT_BRANCH_NAME`은 해당 브랜치 훅에 그대로 전달한다. 명세 생성 자체에는 브랜치 생성을 강제하지 않는다.
6. 템플릿에 따라 사용자 시나리오, 경계 사례, `FR-###`, `SC-###`, 범위, 가정·의존성을 작성한다. 데이터가 있으면 주요 개체도 작성한다. 사용자 스토리는 우선순위와 독립 검증 방법을 갖추고 실제 의존성은 명시한다.
7. 무엇을 왜 제공하는지 중심으로 작성한다. 사용자가 명시한 기술·외부 인터페이스 제약은 보존하되 구현 설계로 확대하지 않는다. 성공 기준에는 측정 조건·방법을 적고 출시 전 검증과 출시 후 사업 지표를 구분한다. 목표치를 실측 성과로 표현하지 않는다.
8. 중요한 미결정만 `[NEEDS CLARIFICATION: 구체적인 질문]`으로 표시한다. 한 차례에 최대 3개를 우선 제시하되 한도를 넘었다는 이유로 나머지 중요한 결정을 임의 확정하지 않는다. 남은 항목은 명시적으로 보류한다. 합리적 저위험 기본값은 가정과 근거를 기록한다.
9. `checklist-template`을 해석해 `checklists/requirements.md`를 만들거나 갱신한다. 내장 점검표의 소유권 설명은 `specify`·`clarify`가 관리하고 `[x]`는 명세 품질 충족을 뜻한다고 작성한다. 사용자 정의 점검표의 검토자 전용 문구를 그대로 복사하지 않는다. 아래 기준을 실제 명세와 대조한다. 실패한 내용은 최대 3회 수정·재검토하고 남은 문제를 보고한다. 질문이 필요한 항목은 사용자의 답을 기다리거나 `$speckit-clarify`로 넘긴다. 미완료 점검표가 명확화 자체를 차단하지 않는다.

## 내장 명세 품질 기준

- 사용자 가치와 범위·제외 범위가 명확한가?
- 필수 섹션이 채워지고 요구사항과 인수 기준이 모호하지 않으며 검증 가능한가?
- 각 기능 요구사항을 관련 스토리 또는 인수 기준으로 추적할 수 있는가?
- 핵심 흐름과 관련 경계·실패 사례가 정의되어 있는가?
- 성공 기준에 측정 방법·조건이 있고 근거 없는 수치나 구현 성과 주장이 없는가?
- 가정·의존성과 사용자가 지정한 제약이 구분되어 있는가?
- 불필요한 구현 설계와 미해결 `[NEEDS CLARIFICATION: ...]`이 남지 않았는가?

점검표는 명세와 분리한다. 통과 여부는 근거로 판단하고 질문 답변을 반영하면 다시 검토한다.

## 완료 보고

`SPECIFY_FEATURE_DIRECTORY`, `SPEC_FILE`, 품질 점검 결과와 미해결 사항을 보고한다. 중요한 미결정이 있으면 명확화를, 준비되었으면 `$speckit-plan`을 안내한다. 훅 결과까지 확인해야 완료다.
