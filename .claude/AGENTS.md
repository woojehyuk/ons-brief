# AGENTS.md

## 답변원칙
- 기본적으로, 핵심적인 내용 위주로 개조식으로 답변
- 여러 옵션을 비교할 때는 표 형식을 사용하여 직관적으로 표현
  - 표나 불릿포인트를 사용할 때에는 명사형 종결로 작성
- 증감, OX, 체크, 중요 등의 표시는 이모지를 사용하여 표현
- 낯선 용어는 짧게 풀어 쓴다. 비교는 표, 실행 순서는 목록을 사용
  - 사용자는 비 IT 직군으로 가정하며, 추가적인 설명을 같이 제공
  - 모호한 값을 정할 때는 추천값을 같이 제안
  - 설명을 할 때에는 구조를 직관화하여 표현하여 사용자의 이해를 돕기
- 모호한 부분은 사용자에게 모호하다고 솔직하게 표현
- 사용자가 제시하지 않은 내용을 함부로 억측 금지.

## 문서 작성 원칙
- 모든 문서는 핵심적인 내용 위주로 개조식 + 명사형 종결 로 작성
- 문서 라인은 200줄을 넘지 않도록 하며, 넘어야 할 경우 파일을 나누어 작성
- 문서는 `docs` 폴더를 만들어, 해당 폴더에서 관리. 
- 문서는 간결하게 유지하되 파일 개수 제한은 없음. 같은 내용을 중복 관리 지양.

## 기본 스택과 구조
기본 스택은 아래를 따르며, 사용자가 원하는 경우 변경 가능

## 프로그래밍 원칙

### Tech Stack
- Frontend : Vite + TypeScript + React 
- Backend : python fastapi
  - BE 없이 구현 가능한 프로젝트라면 BE 를 사용하지 않음. 이 점을 사용자에게 명시.
- Database : Sqlite

### 코드 작성 원칙
- **Simplicity First** 
  - 핵심적인 로직 위주로, 간단하게 코드를 작성
  - 사용자의 서비스 구조에 BE 가 필요없다면, 처음 구조를 선택할 때 이를 안내. 한번 기술스택이 정해진 이후로는 다시 안내 X
- 배치 스크립트 제작
  - 코드 작업이 끝나면, 서버를 실행할 수 있는 배치 스크립트를 작성
  - window 환경에 맞게, CRLF 에 유의하여 작업.
  - ex : start.bat, stop.bat
- LLM API 사용 관련
  - `.env.example` 파일과 `.env` 를 만들고, 사용자에게 `.env` 에 KEY 를 채워넣으라고 안내.
  - 기본은 `OPENAI_API_KEY` 를 사용하며 기본 모델은 `gpt-6-luna` 를 사용합니다.
  - 반드시 코드를 작성하기 전, 최신 APIKEY 활용 문법을 확인합니다. (ex : 파라미터 등)
  - 기존 `.env`·`.env.local`을 덮어쓰지 않음. `.env.example`에는 변수명과 빈 값·예시만 기록.
  - 큰·DB 비밀번호·서버 전용 키를 대화·로그·커밋에 출력 금지. 필요한 인증 입력은 사용자에게 안내
- 프로그래밍 첫단계 (스캐폴드 + UI)
  - 스캐폴드를 기장 먼저 작성
    - 필요한 라이브러리를 설치하고, 라이브러리 동작도 테스트. 
    - 특히 외부 API 이용에 대해 테스트해보고, CORS 나 네트워크 이슈가 있는지 확인.
    - fe, be, db 스캐폴드간의 연결을 테스트. 
  - 이후 UI-First 를 결합하여 UI 를 이어서 작업 
    - UI 작업은 `ons-ui-designer` 스킬 사용
    - UI 는 라우팅 및 구조 수준까지 구체화하여 시작
- 테스트 원칙
  - 코드 작업이 끝나면, 단계마다 테스트를 진행
  - 테스트가 끝나면 점유하는 테스트 프로세스(ex : vite 5173) 를 종료 
- 외부 의존성 활용
  - 외부 API 문법은 구현 시 공식 문서로 확인하고 비밀 키가 필요한 호출은 서버 측에서 처리한다.
- 배포 원칙
  - 배포는 사용자가 원할때만 진행하며, 기본적으로 Vercel (FE) + CloudFlare Quick Tunnels (BE) 를 사용
  - FE : Vercel 배포를 진행하며, 
  - BE : 추후 사용자가 원할 때 CloudFlare Quick Tunnels 배포
  - UI 에 backend 주소를 입력할 수 있게 하여, BE 및 DB 연동 버튼을 UI 에 구현한다. 
- 코드 관리 원칙 (Git) 
  - 코드 작업이 끝나면 사용자에게 Git commit 여부를 문의 
  - commit & push 는 모듈단위 이며, 세부적으로 진행하기 보다는 Phase(step) 별로 진행

## 폴더 구조
- 폴더 구조
  - docs : 원본 문서들 (ex : PRD 등)
  - data : 프로젝트에 활용될 데이터 모음 
  - project : 만들어진 소스코드 결과물을 해당 디렉토리에 넣기
    - frontend : 프론트엔드 디렉토리
    - backend : 백엔드 디렉토리
    - output : 프로그램으로 부터 만들어진 산출물 기본 저장폴더 (ex : 완성된 보고서 docx 파일 등)
  - spec : source 로 부터 만든 개발 계획서들. LLM 이 개발에 활용할 지식의 원천
